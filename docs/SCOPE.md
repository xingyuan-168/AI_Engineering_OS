# Codex AI Engineering OS 项目边界

版本：V2.0-derived
状态：可执行文档基线
目标形态：个人本地 AI 软件研发操作系统

## 1. 目标

将用户提出的业务目标转化为一条可追踪的软件交付链路：需求分析、开源调研、产品和交互设计、架构设计、技术选型、任务拆分、Agent 协作、编码、测试、Review、发布和经验沉淀。

首个可验证目标是：用户输入“开发一个 ERP 采购模块”，系统能够生成项目文档、选择 Workflow、拆分任务、执行受控开发、完成质量检查，并留下可回溯的决策和发布记录。

## 2. MVP 范围

### 2.1 必须实现

- 本地 Git 项目初始化和标准 `docs/` 文档骨架。
- 项目目标、复杂度和风险级别识别。
- `new-project`、`feature-development`、`bug-fix`、`release` 四条 Workflow。
- 文档驱动的状态机：暂停、恢复、失败重试和事件记录。
- Skill 和 Agent 的统一配置契约。
- 基于 Git Branch/Worktree 的任务隔离。
- 受控命令和文件执行，支持 dry-run 和关键操作人工确认。
- 需求变更影响检查：API、数据库、架构、ADR 和 CHANGELOG。
- 测试、代码 Review、安全检查和发布候选物生成。
- 基于 Markdown、ADR、CHANGELOG 和 SQLite 事件日志的第一版 Memory。
- 开源项目调研记录和 License 审核门禁。

### 2.2 首期支持的项目类型

- 通用后端项目。
- 通用前端项目。
- 前后端一体项目。
- 小型到中型功能开发。
- 需要多角色协作的复杂项目试点。

### 2.3 暂不实现

- 面向多人组织的 SaaS 控制台、租户和计费系统。
- 无人工确认的生产环境自动部署。
- 让多个 Agent 在同一工作目录中并行写入。
- V1 阶段的向量数据库、复杂知识图谱和自动长期记忆重写。
- 自研通用大模型或替代所有外部开发工具。
- 将所有开源项目同时作为运行时依赖。

## 3. 自动化边界

### 可自动推进

- 文档模板生成和完整性检查。
- 低风险代码修改、格式化、单元测试和静态检查。
- Workflow 状态更新、任务分发和结果汇总。
- 开源候选项目的资料收集和初步对比。

### 必须人工确认

- 需求和范围冻结。
- 架构、技术栈和重大 ADR 确认。
- 外部开源依赖引入、License 不确定或高风险依赖变更。
- 数据库破坏性迁移、敏感数据处理和安全策略变更。
- 生产发布、回滚和不可逆命令。

## 4. 非目标

本项目不是“只要输入一句话就无条件生成生产系统”的黑盒工具。系统必须保留设计依据、执行记录、测试证据、人工审批和失败经验；当信息不足或风险超过策略时，应暂停并请求确认。

## 5. 成功标准

- 新项目能在一次初始化流程中生成所有必需文档和项目状态。
- 任一功能变更都能输出影响检查结果，并指出需要更新的文档。
- 每个 Agent 任务都有输入、输出、允许路径、分支和 Review 结果。
- 发布候选物能够关联需求、提交、测试、Review、安全检查和 CHANGELOG。
- 开源复用决策能够追溯到候选项目、版本、License、分析结论和 ADR。
- 关键门禁无法被静默绕过，失败流程可以恢复。

## 6. 约束与假设

- 首期运行在个人本地 Git 仓库和 Codex 工作流中。
- 文档、配置和决策记录纳入版本控制。
- V1 采用文件和 SQLite 优先的实现，保持后续迁移到团队服务的可能性。
- 真实项目试点前，必须完成开源 License、命令执行和敏感信息策略评审。

## 7. 范围变更规则

任何新增能力必须说明目标、用户价值、涉及模块、文档影响、风险、测试方式和是否需要新的 ADR。未完成影响检查前，不进入实现阶段。

## 8. 完成定义

本边界文档已明确 MVP 必须实现、暂不实现、自动化边界、非目标、成功标准和变更规则。后续新增事项必须进入“范围变更记录”，不得通过口头约定扩大范围。
