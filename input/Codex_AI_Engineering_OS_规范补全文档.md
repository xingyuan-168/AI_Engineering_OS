# Codex AI Engineering OS 项目规范补全文档

## 文档目的

本文档用于指导 Codex / DeepSeek Harness AI Engineering OS 项目规范补全。

根据当前项目规范审查结果，现有文档体系已经覆盖：

-   项目需求
-   架构设计
-   API规范
-   数据库规范
-   UI设计
-   Agent规范
-   Workflow规范
-   工程流程

但为了满足最终目标：

> 构建一个可长期运行、可自动执行、可扩展到 DeepSeek Harness 插件体系的
> AI 软件工程操作系统。

仍需要补充以下文档。

------------------------------------------------------------------------

# 一、MEMORY_SPEC.md

## 为什么需要补充

当前项目已经定义 Memory 概念，但缺少详细规范。

如果没有 Memory 规范，会导致：

-   AI保存大量无价值聊天记录。
-   项目经验无法复用。
-   不知道哪些信息应该长期保存。
-   不同项目之间无法形成知识积累。

Memory 是整个 AI Engineering OS 区别于普通 Coding Agent 的核心能力。

------------------------------------------------------------------------

## 补充目标

定义：

-   什么需要记忆。
-   什么不应该记忆。
-   什么时候写入。
-   如何检索。
-   如何更新。

------------------------------------------------------------------------

## 文档内容

建议结构：

``` text
MEMORY_SPEC.md

├── Memory目标
├── Memory分类
├── 数据结构
├── 写入规则
├── 检索规则
├── 生命周期管理
└── 清理规则
```

------------------------------------------------------------------------

## Memory分类

### 1. Decision Memory

保存：

-   架构决策
-   技术选型
-   设计原因

例如：

为什么选择 PostgreSQL。

------------------------------------------------------------------------

### 2. Project Memory

保存：

-   项目结构
-   模块关系
-   当前状态

------------------------------------------------------------------------

### 3. Bug Memory

保存：

-   已解决问题
-   原因
-   解决方案

------------------------------------------------------------------------

### 4. Experience Memory

保存：

-   开发经验
-   最佳实践
-   失败案例

------------------------------------------------------------------------

## 写入触发条件

以下事件自动写入：

-   ADR创建
-   Bug解决
-   Release完成
-   重大技术决策
-   架构变更

------------------------------------------------------------------------

# 二、PLUGIN_SPEC.md

## 为什么需要补充

当前目标已经从：

Codex规范系统

扩展为：

DeepSeek Harness插件。

因此必须明确插件边界。

否则未来开发会出现：

-   重复实现Harness能力。
-   插件侵入核心。
-   模块职责混乱。

------------------------------------------------------------------------

## 补充目标

定义：

哪些能力属于 Harness。

哪些能力属于 AI Engineering OS 插件。

------------------------------------------------------------------------

## 文档内容

``` text
PLUGIN_SPEC.md

├── 插件定位
├── 生命周期
├── 接入方式
├── Hook定义
├── 数据接口
└── 权限边界
```

------------------------------------------------------------------------

## 边界定义

DeepSeek Harness负责：

-   模型调用
-   Session管理
-   Tool Runtime
-   Agent执行环境

插件负责：

-   项目管理
-   Workflow
-   Skill
-   Memory
-   工程规范
-   文档管理

------------------------------------------------------------------------

# 三、WORKTREE_SPEC.md

## 为什么需要补充

复杂项目需要多Agent并行开发。

如果没有Worktree规范：

-   Agent互相覆盖代码。
-   分支混乱。
-   无法安全合并。

------------------------------------------------------------------------

## 补充目标

定义：

什么时候创建Worktree。

如何管理。

如何合并。

------------------------------------------------------------------------

## 文档内容

``` text
WORKTREE_SPEC.md

├── 创建条件
├── 目录结构
├── Branch规则
├── Agent权限
├── 合并流程
└── 清理规则
```

------------------------------------------------------------------------

## 示例

``` text
.worktrees/

frontend-agent/

backend-agent/

database-agent/

qa-agent/
```

------------------------------------------------------------------------

# 四、AGENT_HANDOFF.md

## 为什么需要补充

当前已有Agent角色定义。

但是缺少Agent之间交接标准。

没有交接规范：

-   上游输出不明确。
-   下游无法继续。
-   多Agent协作失败。

------------------------------------------------------------------------

## 补充目标

定义：

每个Agent必须输出什么。

------------------------------------------------------------------------

## 示例

Architect Agent输出：

-   ARCHITECTURE.md
-   API_SPEC.md
-   DATABASE.md

Backend Agent交付QA：

-   修改文件列表
-   Commit记录
-   测试结果

------------------------------------------------------------------------

# 五、WORKFLOW_ROUTING_RULES.md

## 为什么需要补充

当前Workflow定义了：

如何执行。

但是缺少：

什么时候选择哪个Workflow。

------------------------------------------------------------------------

## 补充目标

实现自动流程选择。

------------------------------------------------------------------------

## 示例规则

简单任务：

复杂度 \< 5

使用：

feature-development

复杂任务：

复杂度 \>= 7

使用：

large-project

涉及前端：

启用：

frontend-project

涉及多人：

启用：

Worktree + Multi-Agent

------------------------------------------------------------------------

# 六、BOUNDARY_SPEC.md

## 为什么需要补充

当前最大问题：

模块都有，但是边界不够明确。

需要防止：

-   Project Manager修改代码。
-   Skill修改全局状态。
-   Agent越权。

------------------------------------------------------------------------

## 补充目标

定义模块职责边界。

------------------------------------------------------------------------

## 示例

Project Manager：

可以：

-   分析需求
-   调度流程

不能：

-   修改业务代码

Workflow：

可以：

-   编排任务

不能：

-   决定业务方案

Skill：

可以：

-   生成专业产物

不能：

-   修改项目规则

------------------------------------------------------------------------
